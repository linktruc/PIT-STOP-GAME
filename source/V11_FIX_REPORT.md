## Bot timing: authority, bootstrap and presentation

A newly eligible bot uses the arithmetic mean of valid real-human unlock-to-click samples already recorded at its eligibility time. A scheduled task keeps its dueAt; later samples influence future tasks, not an already scheduled deadline. Opening-jack synchronization and the simultaneous-human cohort cap can legitimately complete a bot earlier, with a diagnostic reason. Effective timestamps, not polling/render time, determine score.

Solo FRONT_JACK can contribute the first real sample immediately after GO; a 4,000ms input must seed dependent tasks at 4,000ms, while a 250ms comparison must differ. A non-jack Solo role can require prerequisite bots before any human sample exists: those tasks use scoped bootstrap, then newly eligible tasks use the real sample once available. This causal difference is documented, not represented as a permanent 400ms policy.

Online `pit_private.reconcile_round` already implements the required reference behavior. **No new SQL migration is required for V11.3.** Nine complete-round fixtures cover TS/SQL parity, evolving means and the cohort cap; inherited early-lockout, jack-sync and migration suites also passed targeted backend checks. The final integrated suite remains the authoritative total. The precise TypeScript tie-case change only aligns its diagnostic completion reason to SQL; it does not alter completedAt or official score. Physical work poses must wait for the event-appropriate moment; their short duration and any visual tail remain outside GO-to-release scoring.

The actual local test output is `docs/v11-evidence/bot-timing-report.json`, with 21 task rows per fixture recording baselineMeanMs / enabledAt / dueAt / completedAt / reason / source. Times below are milliseconds relative to GO:

## Global administrator setup and identity safety

Use the existing confirmed Supabase Auth user, its unchanged UUID/alias and actual current password. V11.3 submits that password to Auth without an arbitrary 12-character frontend rejection. A strong private password is recommended; updating does not require a reset. Admin Access is available from the main menu and leaderboard regardless of Solo. Server allowlisting, confirmation, auditing and linked online deletion remain required. Missing backend connectivity yields a clear backend-required state.

Solo retains its in-memory gameplay identity while global admin state is fetched separately; it does not replace the Auth identity. Client-local snapshots, including the empty state after leaving Solo/practice, cannot overwrite verified global admin state. Auth/delete revisions and serverNow ordering discard stale reads and request a fresh global snapshot. Global polling stays separate from local gameplay heartbeat, with coalesced single-flight realtime reads. An existing online membership must be explicitly left before sign-in/sign-out changes Auth. The sign-in form requires a checked warning before **Leave Team & sign in**; an active attempt ends, while completed results stay saved. Without that acknowledgment, submission is disabled. Returning to the menu retains the seat. No silent seat reassignment is permitted.

`admin-watch-report.json` exercises the actual app and Supabase JS Auth/session persistence against controlled HTTP responses, including alias resolution and the six-character fixture password reaching Auth. The Realtime socket is a local no-op in this harness; HTTP refresh/recovery drives subsequent invalidation. This is integration proof for transport/UI behavior, not a claim that the owner's hosted account was used. The retained real PostgreSQL tests cover permission enforcement, auditing and atomic linked deletion separately.

[V11_ADMIN_SETUP.md](V11_ADMIN_SETUP.md) gives exact allowlist/alias SQL and email-confirmation/UUID checks. [V11_3_DEPLOY_GUIDE.md](V11_3_DEPLOY_GUIDE.md) gives every supported upgrade sequence, runtime config, Netlify steps and the retained 45-second disconnected / 15-minute lobby-grace defaults.
