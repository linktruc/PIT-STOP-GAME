4. PREMATURE ACTION TAP PENALTY: EXACTLY 2 SECONDS
============================================================
Introduce an intentional gameplay anti-spam rule: pressing the MAIN ACTION BUTTON before one's action is available imposes a 2,000ms personal lockout.

BEHAVIOR:
- Only the player's primary action control during COUNTDOWN/RUNNING can incur the penalty. Menu, Ready, Start, Rotate, settings, chat, details and other UI never incur it.
- In RUNNING, when player has an outstanding assigned task but it is LOCKED, clicking the disabled-looking ('HOLD') action button should COUNT as a premature attempt.
- In COUNTDOWN, pressing the early-action control likewise incurs penalty; the remaining lockout at GO must be 2s from GO at minimum (do not silently let the 2s expire before GO). This must be clearly communicated.
- Once penalized, show concise feedback 'TOO EARLY · +2s LOCKOUT' / 'PENALTY 1.8s' as a countdown over/inside the action button, with short audible error cue and modest red/orange flash. Do not spam global notification dialogs.
- If the task becomes AVAILABLE during lockout, still deny completion until lockout expires. Once over, button activates. The official shared pit stop clock CONTINUES RUNNING during penalty, naturally increasing elapsed time. Do NOT simply add 2s to final result or pause the whole team.
- Penalty is PER HUMAN PLAYER and PER ROUND; other players and bots continue unaffected except through normal task dependencies. When player's previous task is done and their next owned task is still locked, a new early tap can penalize that upcoming action.
- Repeated premature taps while already penalized are ignored (do not stack the delay endlessly); debounce taps to avoid accidental double penalty.
- Taps after ALL of that player's actions are completed must not cause penalty.
- Accessible disabled-looking button should still capture the intended pointer click while not ready; do not use native HTML disabled on this particular early-tappable HOLD state. Retain true disabled for pending RPC if appropriate. Keyboard Space must follow the same penalty policy, with guards against typing-focused elements and key repeat.
- Cross-device persistence: a short disconnect/reconnect must not reset an active penalty; repeated request IDs must be idempotent. Compute penalty_until and validity using the SERVER clock for online rooms, never trusted client timestamps.
- Add an additive Supabase SQL migration for server authoritative early-tap recording/lockouts, rather than relying on frontend state only. Validate role ownership; reject illicit early penalties on arbitrary other players. Only the actual owner can incur their own lockout and complete tasks.
- The local reference engine (`src/engine.ts`), SOLO mode (`src/solo.ts`), browser-only practice (`src/practice.ts`) and production SQL MUST implement equivalent behavior and tests. Use existing API channel or an explicit new 'early_action' op; do not break the normal accepted-action path.
- Ensure the server rejects accepted actions during penalty even if a request directly calls the RPC bypassing the UI. Handle network timeout/duplicate request without accidentally double-applying penalty.
- Early tapping must NEVER change bot due time directly, ignore the 21-task DAG, or prematurely mark a stage DONE. Human reaction times after a penalty are still naturally reflected in timing if the action was unlocked earlier.
