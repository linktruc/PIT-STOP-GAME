G. FIX READY RESET, RANDOM ROLE SWITCH, AND CONNECTION INSTABILITY
====================================================================
ROOT CAUSE TO INVESTIGATE (DO NOT GUESS):
- The current SQL pit_private.assign_roles() randomly reallocates ALL roles and clears ALL Ready flags whenever called.
- It is called on joins and member removals. This is why roles can switch and Ready can clear even if a player never touched the controls.
- WAITING membership is removed at last_seen_at older than 90 seconds; mobile/tab suspension or failed RPC could trigger this.
- src/useGame.ts sends heartbeat every 250ms whenever *any* room races, leading to RPC contention and many redundant snapshots.

REQUIRED SERVER-SIDE FIX:
1. Roles must become STABLE after first assignment. Joining a WAITING room assigns ONE unused playable role to the new member without rerolling existing members.
2. Guarantee at least one real jack as the first joined player or through a transparent initial assignment rule. Roles remain unique; max 15.
3. On normal join, do NOT reset existing ready states if their roles have not changed. The joining person starts Not Ready; host Start still requires every member Ready.
4. When a player leaves/is kicked in WAITING, preserve all unaffected members' roles and readiness. If the last human jack leaves, perform the MINIMUM necessary explicit reassignment and notify only the affected person; readiness of reassigned person may be cleared with explanation.
5. Replays need not reroll roles. Prefer “Same crew, same roles” as default; if a new randomization button is intentionally added, it must be host-controlled and visibly reset Ready for reassigned people.
6. Prevent silent role changes following network reconnect or tab background/foreground. Client should retain server-stable playerId/session.
7. Adjust WAITING inactivity to account for mobile suspension. Provide explicit disconnection indicator and generous configurable grace; do not kick an ordinary player after only a brief network glitch. At the same time, allow host to remove stale users; choose a documented, tested timeout policy.
8. Preserve authorization/capacity/unique roles/atomicity and no unintended bypass of server checks. SQL migration must be idempotent and avoid dropping results.

REQUIRED CLIENT FIX:
1. Replace global 250ms polling with efficient Realtime-triggered refresh (debounced/coalesced), slower fallback fetch/heartbeat and jittered exponential backoff on errors. A running local UI timer should interpolate smoothly between authoritative timestamps without spamming RPC.
2. Realtime reconnect and auth token refresh must be robust across iOS Safari background/foreground events; protect against out-of-order snapshots.
3. Do not show stale data as live without a subtle “Reconnecting…” indicator. Preserve last known room/role while reconnecting; avoid flashing the menu or assigning another role based on a transient empty response.
4. Do not issue duplicate action RPCs after the first one is accepted. Show pending state, recover safely from timeout; backend idempotency must remain enforced.
5. Fix any race between refresh() and run() and repeated auth/session changes. Log useful diagnostics but never expose credentials in logs.
6. If an actual server timeout and host handoff occur, inform affected players clearly rather than silently changing roles/Ready.

TEST MULTI-DEVICE CASES:
- 4 people Ready; 5th joins: existing four remain Ready and keep roles, newcomer Not Ready.
- A waiting member leaves: everyone else's role and Ready remain unless indispensable jack reassignment occurs.
- Two phones backgrounded for >2 minutes and return: no unjustified role switch/reset; behavior according to documented longer grace.
- Multiple rooms active: no 250ms-per-device RPC storm.
- Reconnecting on flaky network recovers without duplicate player seat.
- Stable start, host kick, replay, 4–15 cap, parallel bot rules, leaderboard persistence.
